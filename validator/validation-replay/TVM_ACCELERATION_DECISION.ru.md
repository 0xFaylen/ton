# Решение по ускорению TVM на одном шарде

Дата среза: 2026-07-31.

## Вывод

Trace JIT для стандартных кошельков пока не является основным проектом. На
измеренном тяжёлом наборе Wallet V5 R1 и Wallet V4 R2 действительно являются
горячими, но 72–82% их времени уходит в Ed25519, а не в интерпретацию TVM.
Даже идеальное устранение всего остального времени этих двух хешей ускорило бы
TVM-часть набора не более чем примерно в 1,11 раза. Реальный JIT даст меньше.

Это не доказывает, что JIT бесполезен для всех контрактов. Это закрывает более
узкую гипотезу: «стандартные кошельки горячие, значит компиляция кошельков даст
крупный прирост».

Следующий обоснованный этап — построить матрицу
`code_hash × expensive primitive × wall time` и искать горячий остаток без
криптографии. Переход к trace JIT разрешается только после измерения доли TVM в
полном критическом пути коллации и валидации.

## Что измерено

Инструмент `tvm-replay-bundle` повторно исполняет исторические транзакции и для
каждой из них требует совпадения:

1. хеша сериализованной транзакции;
2. хеша результирующего состояния аккаунта.

Флаг `--profile-ed25519` не пропускает проверку подписи и не меняет gas. Он
измеряет время внутри реального `Ed25519::PublicKey::verify_signature`. В обычной
коллации и валидации внутренний таймер выключен.

### Полный блок

- Блок: `(0,8000000000000000,87341675)`.
- Scope: `full_block`.
- Аккаунты: 29 из 29.
- Транзакции: 51, все 51 исполнили TVM.
- Результат: точное совпадение transaction hash и account-state hash.
- Один Release-прогон: TVM 10,833 мс, Ed25519 2,647 мс, 5 проверок.

Один прогон подтверждает корректность пути, но не является устойчивым
performance baseline.

### Тяжёлый account subset

- Блок: `(0,8000000000000000,87341719)`.
- Scope: `account_subset`.
- Аккаунты: 68 из 77. Девять доказательств были исключены как относящиеся к
  состоянию после требуемого predecessor block.
- Транзакции: 92, из них 87 исполнили TVM.
- Результат каждого прогона: точное совпадение transaction hash и account-state
  hash для всех включённых аккаунтов.
- Метод: Release, два прогревочных запуска и десять измеряемых запусков.

## Потолки, а не прогнозы

Остаток без Ed25519:

- Wallet V5 R1: `4,391 - 3,150 = 1,241` мс;
- Wallet V4 R2: `2,278 - 1,870 = 0,408` мс;
- вместе: 1,649 мс, или 9,57% всей TVM-части набора.

Если JIT бесплатно устранит весь этот остаток, что физически невозможно,
ускорение TVM-части составит:

```text
17,232 / (17,232 - 1,649) = 1,106x
```

Это строгий верхний предел только для компиляции двух стандартных кошельков на
этом workload. Он не включает сеть, CellDB, Merkle update, сериализацию и другие
части критического пути блока. End-to-end выигрыш будет ниже.

Хеш Config45 не выполняет Ed25519 и занимает 2,638 мс. Его идеальное бесплатное
ускорение до нуля дало бы не более 1,181x TVM на этом наборе. Нативной реализации
этого хеша в публичных `master` и `testnet` на дату среза нет, но реализация
сложного контракта только ради такого потолка пока не оправдана.

#2485. Он также не улучшает сеть и не должен выдаваться за рост shard TPS.

## План с закрытыми гейтами

### Этап 1. Primitive Ceiling Matrix

Добавить только в offline exact replay время и число вызовов дорогих семейств:

- Ed25519, secp256k1/P256 и BLS;
- extended hash operations;
- dictionary operations;
- cell hashing, загрузка и создание ячеек;
- library resolution.

Приёмка:

- обычный runtime не запускает внутренние таймеры;
- A/B overhead профилирования не больше 2% на устойчивом Linux replay host;
- точные transaction/state roots на каждом прогоне;
- минимум несколько блоков разных типов нагрузки;
- атрибутировано не менее 90% TVM wall time горячих хешей.

### Этап 2. Выбор одного механизма

1. Если несколько стабильных code hashes без криптографии занимают не менее
   25% полного critical-path wall time, сделать одну нативную ceiling probe.
2. Если хеши разнообразны, но доминирует декодирование и dispatch TVM, проверять
   cached decoded blocks/superinstructions до trace JIT.
3. Если TVM меньше 30% полного критического пути, остановить VM-трек и перейти к
   коллации, Merkle/state или сети согласно измеренному лидеру.

Native probe выполняется только офлайн. Узлы с разными native-реализациями могут
получить разные roots, поэтому общий testnet запрещён до дифференциального
доказательства эквивалентности.

### Этап 3. Полный critical path

Запустить `ValidationReplayer` на отдельной копии полной C++ validator DB:

- `collate` и `validate` раздельно;
- одинаковый короткий диапазон блоков;
- один job для exact timing;
- wall time, а не доля CPU;
- сеть и consensus в результат replay не входят и измеряются отдельно.

Текущий локальный диск не подходит: доступный persistent-state corpus требует
примерно 65 ГБ только для исходных BOC/parts, а импорт в CellDB требует
дополнительное место. Производственную mainnet-ноду нельзя использовать как
replay host. Нужен отдельный диск или отдельный узел с запасом не менее 200 ГБ.

### Этап 4. Большой проект

Крупная архитектурная работа разрешается только после этапов 1–3. Кандидат —
детерминированное execute/commit-разделение по аккаунтам, использующее отсутствие
синхронных cross-contract reads в TON. До прототипа должны быть формально закрыты:

- непрерывный `ProcessedUpto` при частично завершённых аккаунтах;
- глобальные gas/byte/lt/transaction limits;
- детерминизм при одинаковом наборе сообщений;
- serial fallback до дедлайна, не создающий цикл пустых блоков;
- повторное исполнение ValidateQuery;
- совместимость с dedicated collators из #2485.

Без решения первого пункта параллельный collator не является рабочей
архитектурой. Поэтому этот этап нельзя начинать с распределённых workers или
remote execution.

## Что не доказано

- Текущий устойчивый mainnet TPS одного шарда.
- Доля TVM в полном wall-clock critical path коллации и ValidateQuery.
- Выигрыш JIT, native contracts или account-parallel execution на mainnet.
- Пропускная способность Plumtree/валидации для блоков 4–10 MiB.
- Безопасность увеличения block limits.

До закрытия этих пунктов любые числа TPS являются целью или оценкой, но не
результатом.
