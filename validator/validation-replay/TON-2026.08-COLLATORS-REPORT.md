# TON 2026.08 "Collators": effect on single-shardchain TPS

Report date: **2026-08-15**. Written before activation, so every forward-looking
statement is falsifiable against what happens on 08-20.

Everything below is split into four confidence tiers, because the honest answer
to "how much does per-shard TPS go up" depends entirely on which tier you accept:

- **TIER A — verified fact.** Read from source code at named refs, or quoted
  verbatim from the publisher. Not open to interpretation.
- **TIER B — our measurement.** First-party, reproducible, with the stand's
  limitations stated.
- **TIER C — arithmetic.** Derived from A and B by stated formula.
- **TIER D — unknown.** Named explicitly rather than filled with a plausible number.

---

## 0. The one-line answer

**TON Core published no number.** Not a percentage, not a multiplier, not a
before/after. The single quantity that follows from mainnet-measured inputs is
**~10x on a shardchain that is currently collating cold** — and it is conditional
on operators enabling in-memory celldb, which this release does not ship,
configure, or document.

On an already-warm shardchain, this release delivers **no directly measurable
TPS increase**; it delivers a capability (collation on separate hardware).

## TIER A — Verified facts

### A1. What was announced

@toncore #118, 2026-08-12 14:14 UTC, the channel's most recent post. Three
throughput statements, all qualitative, two future tense:

1. "Currently, validators both assemble blocks from user transactions and
   validate them. After the update, these responsibilities will be separated.
   Dedicated collator nodes will assemble blocks, while validators will only
   verify them. **This separation increases network throughput.**"
2. "**Enabling collators, particularly in in-memory mode, will increase the
   maximum TPS of a single shardchain.**"
3. "As the next step, we plan to increase the maximum block size and other
   network limits... **Increasing the limits will also lead to a proportional
   increase in the TPS of a single shardchain.**"

**Post #118 contains no numbers at all.**

Schedule (@tonstatus #235, 2026-08-12): software **08-17 14:00 UTC**, config vote
**08-18 12:30**, mytonctrl update and activation **08-20 12:00**. Mandatory for
validators; full nodes unaffected.

### A2. TON Core's other published multipliers are NOT TPS

From @toncore #115 (2026-07-17): 10x faster operations (consensus/latency), 6x
fee reduction, 2-4x network-traffic reduction. None is a throughput figure. The
only TPS numbers TON Core ever published are from #99 (2026-03-06, **five months
before this announcement and pre-collator**): "with 1,000 transactions per second
in a single shardchain, the operation time remains less than a second" in testnet
load testing, against "~500" as the historical mainnet peak.

### A3. Role separation is real and shipped

- PR #2523 "Collators" merged into `testnet` **2026-08-07**; `CollationManager`
  is entirely removed from `testnet` and replaced by native delegation.
- Delegation is of the **whole leader window**, not per block
  (`validator/consensus/block-producer.cpp:121` `prepare_delegation`), with a
  `pleaseCollatePrepare` fan-out, a scoreboard picking among live collators, and
  exponential banning (60 s to 3600 s) on missed windows.
- **Every validator still validates every candidate**, including the delegating
  leader — `validator/consensus/block-validator.cpp:81-105` calls
  `validate_block_candidate` unconditionally; there is no self-produced or
  delegated skip path. **Only candidate generation relocates.**
- Delegation is **shardchain-only**; collators are excluded from masterchain
  groups.

### A4. Nothing makes collation itself cheaper

`master..testnet` is 20,197 insertions across 132 files, of which
`validator/impl/collator.cpp` receives **39 lines from a single commit,
"metrics: expand blockchain observability"** — `ScopedRealCpuTimer` around
dispatch/import phases plus stats fields. `validator/db/celldb.cpp` gains 7 lines
that skip meta validation under `TON_TONTESTER=1`.

**No algorithmic change to the collation hot path.** Collators move work to
another machine; they do not make the work cheaper.

### A5. in-memory celldb is NOT shipped by this update

- `--celldb-in-memory` **predates this work** (present at v2026.07 and earlier),
  defaults to **false** (`validator/validator-options.hpp:349`), help text:
  "store all cells in-memory, much faster but requires a lot of RAM."
- **Zero linkage to any collator code path**, config template, or doc.
- **mytonctrl has no in-memory celldb setting at all.** Its collator PR #589
  additionally *removes* shard scoping, so a collator syncs the whole basechain.
- Both docs.ton.org collator pages are accelerator-era text with **no hardware
  requirements, no RAM figures, no celldb guidance, no TPS claims**, and were not
  updated in August 2026.

So announcement point 2's "particularly in in-memory mode" describes an operator
option that this release neither enables, configures, nor documents.

### A6. ConfigParam 46 is required for collators to function

`crypto/block/block.tlb:846,1004-1022` defines `ValRegistryConfig = ConfigParam 46`
(registry contract address, `max_collators_per_validator`). The on-chain registry
is `crypto/smartcont/validator-registry.tolk`. Without param 46,
`get_all_collators()` returns empty, collators never join the private overlay,
and delegation never happens. **The 08-18 vote almost certainly sets param 46**
(inference, well-supported by code), but its contents are unpublished.

### A7. Block limits and block interval are unchanged by shipped code

ConfigParam 22/23 limits untouched; `max_block_size`/`max_collated_data_size`
read from ConfigParam 29 unchanged; block interval unchanged. The one limits
knob — commit `5f1934f5` "Override block limits in collator options", adding
node-local per-axis overrides — is **on the `collators` branch, unmerged, with no
PR pointing at it**. Whether it ships on 08-17 is unknown.

Its ceiling, precisely: `ValidateQuery` re-derives limits from ConfigParam 22/23
and enforces `gas.hard` (`validate-query.cpp:6107`) and `lt_delta.hard` (`:2456`),
so those axes cannot be raised node-locally. There is **no validator-side byte
check**, so the byte axis can be raised locally up to the ConfigParam 29
candidate cap.

## TIER B — Our measurements

Stand: single validator, tontester network, **mainnet-parity ConfigParam 23**
(bytes soft 1 MiB / hard 2 MiB, gas soft 10M / hard 20M), 400 ms target block
rate, `max_split=0`, 100k wallet-v5 + jetton-wallet pairs, state fully RAM-resident
(115 MB celldb). Hardware: 16 logical cores, 15.8 GB RAM — laptop class.

### B1. Cost model of a block

Bucket-median fit over 125 blocks spanning 0–688 transactions:

| | fixed cost per block | marginal cost |
|---|---|---|
| **mainnet** (our prior telemetry) | **358.7 ms** cold / **1.3 ms** warm | **1.93 ms/tx** |
| **this stand** (RAM-resident) | **2.8 ms** | **0.718 ms/tx** |

### B2. Achieved throughput

At 1200 ext/s offered, 4 connections, mainnet-parity limits:

| | value |
|---|---|
| included | **1,137 raw tx/s = 379 jetton TPS** |
| transactions per block | **649** (median), max 682 |
| block size estimate | **1.74 MB** (median) |
| collation wall | **269 ms** median, 342 ms p90 |
| block cycle | **571 ms** |
| binder | **byte limit** — 98 of 103 blocks over the 1 MiB soft estimate; only 2 of 103 reached the slot |

**Collation is 47% of the block cycle (269 of 571 ms).**

### B3. The limit-increase question is NOT resolvable on this stand

Paired runs at 1200 ext/s, verbosity 1, `block_limit_mul` 1 vs 2:

| arm | runs (raw tx/s) | median | range |
|---|---|---|---|
| mul=1 (soft 1 MiB) | 808, 1135, 1150 | 1135 | 342 |
| mul=2 (soft 2 MiB) | 1251, 896, 1297 | 1251 | 401 |

Median difference is **+10%** in favour of the higher limit, but the ranges
overlap heavily — the best mul=1 run (1150) beats the worst mul=2 run (896) — and
each arm's own spread (342–401, i.e. ±17–20%) is roughly twice the between-arm
difference. **The effect is not resolvable on this stand at n=3.** An earlier
verbosity-3 pair gave the opposite sign (1137 vs 676), consistent with logging
overhead pushing collation past the slot. **No sign, no magnitude claimed.**

Mechanism note that survives the noise: the byte soft limit doubles as a
**deadline guard**. Where collation is slow, removing it lets collation overrun
the slot and throughput falls; where collation is fast, the bigger block fills
in time and throughput rises. That is precisely why in-memory must precede a
limit increase.

## TIER C — Arithmetic

Model: `TPS = (slot − fixed) / marginal × blocks_per_second`, at slot 400 ms and
2.43 blocks/s.

| regime | inputs | tx/block | raw tx/s per shard |
|---|---|---|---|
| cold block, today | 358.7 ms, 1.93 ms/tx | 21 | **~52** |
| warm block, today | 1.3 ms, 1.93 ms/tx | 207 | **~502** |
| our stand (in-memory-equivalent) | 2.8 ms, 0.718 ms/tx | 553 | **~1,344** (~448 jTPS) |

**Point 2's ceiling: ~10x, cold shard only** (52 → 502). This is *restoration* of
capacity that existed before split churn, not a new ceiling. On a warm shard it
is ~1x.

**Point 1's ceiling: up to ~1.9x**, from collation being 47% of the block cycle —
if the remaining 53% fully overlaps on the validator. Upper bound, not a
prediction: the validator still validates, applies state, and runs consensus.

These two do not multiply cleanly: point 2's 10x is measured against a cold
baseline that point 1 also improves.

## TIER D — Unknown

1. **Any percentage TON Core expects.** None published, anywhere.
2. **What the 08-18 vote contains.** ConfigParam 46 is required by code; whether
   the vote also touches ConfigParam 23 (limits), 29, or 12 (`max_split`, cut
   16→4 "temporarily" on 2026-07-15 with announced intent to raise) is unpublished.
3. **Whether the five unmerged `collators` commits ship on 08-17** — no PR, no
   tag, no release branch as of 2026-08-15 13:22 UTC.
4. **Whether operators will run in-memory celldb**, and on what hardware. No
   guidance exists in code, docs, or mytonctrl.
5. **The size of the limit effect** — our stand cannot resolve it (B3).
6. **What fraction of mainnet blocks currently run cold**, which is what scales
   the 10x into a network-level figure. Driven by split churn, not by this release.

## Falsifiable predictions for 08-20

Recorded before activation so they can be scored afterwards:

1. Cold-block fixed cost (~358.7 ms) largely disappears on collator-produced
   shards **if and only if** collators run in-memory. If operators do not enable
   it, expect little change in the fixed cost.
2. Splits per day fall, with the split criterion untouched — `check_block_overload`
   and `history_weight` are byte-identical across `master`, `testnet` and
   `collators`.
3. Per-shard sustained TPS rises toward, but not past, what collation speed
   permits inside the slot. A jump beyond ~500 raw tx/s on a warm shard would
   require either in-memory or a limits change, not role separation alone.
4. Masterchain block rate is unaffected by delegation (shardchain-only).

**Baseline must be frozen before 08-17** for any of this to be scored.

---

## Bottom line

| announcement point | shipped? | our best figure | confidence |
|---|---|---|---|
| 1. Role separation | **yes** | up to ~1.9x (collation = 47% of cycle) | upper bound, ours |
| 2. in-memory | **no** — operator option, undocumented | ~10x on cold shards only, ~1x on warm | arithmetic on mainnet-measured inputs |
| 3. Limits | not in this release | unresolved | our stand cannot separate it from noise |

**Nothing here is a guaranteed percentage.** The mechanism of point 1 is certain;
its magnitude is not. Point 2's magnitude is arithmetically solid but conditional
on a step the release does not perform. Point 3 is unmeasured by anyone publicly.
